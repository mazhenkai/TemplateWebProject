# 提交规范

> 更新时间：2026-11-26

本项目所有 commit 必须遵守本规范。谁能推送见 [`推送与协作规范.md`](推送与协作规范.md)。

## 1. 格式

```
<type>: <简短描述>

<正文：为什么改、改了什么、有什么影响>
```

- `type` 必填，小写，后接**英文冒号 + 一个空格**。可加范围：`feat(frontend): ...`。
- 描述行 **≤ 72 字符**，中文，动词开头，说清"做了什么"而不是"改了哪个文件"，不加句号。
- 正文与描述行之间空一行。正文可省，但**以下情况必须写**：改变行为或输出、改表结构、改配置项、跨模块改动。

## 2. type 取值

只允许下面这些，不自创：

| type | 用途 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(frontend): 订单列表支持按状态筛选` |
| `fix` | 修 bug | `fix(admin): 修复上传空文件时编辑页崩溃` |
| `refactor` | 重构，不改外部行为 | `refactor: 把鉴权逻辑从 handler 抽到中间件` |
| `perf` | 性能优化 | `perf: 订单列表改为分页查询，首屏从 1.8s 降到 0.4s` |
| `test` | 只动测试 | `test: 补充文件上传的集成测试` |
| `docs` | 只动文档 | `docs: 补充部署规范的回滚步骤` |
| `chore` | 构建、依赖、脚本、配置 | `chore(opt): 新增 dev_daily.sh 开关开发环境` |
| `style` | 格式化，不改逻辑 | `style: gofmt` |

既有代码又有文档的 commit，按**代码的性质**归类。

## 3. 描述怎么写

判断标准：**半年后回来看这一行，能不能立刻知道改了什么。**

```
✅ fix: 修复缓存在分页参数为空时不生效
✅ docs: 明确集成测试只打 dev 后端的理由

❌ fix bug                  没说修了什么
❌ fix: 修改代码             等于没说
❌ feat: 增加了一些功能       什么功能
❌ fix: 修复 xx 的问题        "问题"是什么
```

## 4. 正文怎么写

有则写，无则省：

```
为什么改：原接口一次返回全部订单，3000 条时响应 1.8s
改了什么：改为分页，每页 20 条，前端改为滚动加载
影响：旧的 /api/orders 不带 page 参数时默认返回第一页
```

不写空话（"按计划修改""优化代码"），不逐文件描述 diff。

## 5. 一次 commit 只做一件事

描述行里出现「和」「以及」，大概率该拆。允许放在一起的：

- 代码 + 对应的测试（必须同一个 commit，否则测试是红的）
- 代码 + 因这次改动而过时的文档
- 重命名 + 所有引用处的同步修改

拆分后**每个 commit 都要能编译、能跑**，否则 `git bisect` 失效。

## 6. 禁止

- ❌ 提交跑不通的代码
- ❌ 提交密钥、`config/app.env`、`data/`、`log/` 下的内容
- ❌ 一个 commit 跨多个不相关的功能
- ❌ 用 `update` / `change` / `modify` 开头的描述

## 7. 作者与署名

- 提交作者统一使用负责人身份：`<name> <email>`（写入仓库 `git config`）。
- 提交说明**不加** `Co-Authored-By` 等署名行，无论代码由谁或什么工具辅助生成。

## 8. 误提交密钥

**不要只删文件了事**。立刻去对应平台吊销并轮换，再处理仓库，并在当天开发日志记录。git 历史里的东西删不干净。

## 9. 提交前自检

- [ ] `type` 在允许列表内
- [ ] 描述行 ≤ 72 字符、中文、动词开头、无句号
- [ ] 需要正文的情况写了正文
- [ ] 只做了一件事
- [ ] 代码与测试同步提交
- [ ] 没有密钥、真实配置、运行日志
- [ ] `bash opt/linux/check.sh` 通过

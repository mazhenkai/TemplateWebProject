# 部署规范（dev → prd）

> 更新时间：2026-11-26

## 1. 核心原则

1. **代码可以从 dev 发到 prd，数据不行**。数据只允许 prd → dev。
2. **所有变更先在 dev 验证**，再发 prd。
3. **发布只由负责人执行**，AI 助手不跑 `deploy.sh`。
4. **每次发布都记录**在当天开发日志。

## 2. 标准流程

```bash
# 0. 发布前：工作区干净、测试通过、check 通过
git status
bash opt/linux/check.sh

# 1. 构建前端、编译后端
# 2. 表结构白名单同步：先 bash opt/linux/sync_tables.sh 看差异，再 apply 补建缺表
# 3. 手动执行字段变更（如有）：先 dev 验证，再 prd 执行同一条 ALTER
# 4. 重启生产服务
# 5. 访问健康检查与关键页面
bash opt/linux/deploy.sh   # 1、2、4 由脚本完成
```

## 3. 禁止操作

| 操作 | 说明 |
|---|---|
| ❌ 把 dev 库整体同步到 prd | 测试数据会进生产 |
| ❌ 批量导入 dev 数据到 prd | 同上 |
| ❌ 在 prd 直接手写 SQL 改数据 | 无记录、不可回退 |
| ❌ 跳过 dev 直接改 prd 结构 | 两边结构会不一致 |

## 4. 需要确认后才能做

以下操作必须先写清影响范围，负责人确认后执行，并在日志里记录 SQL：

- 数据修复脚本
- prd 的批量更新 / 删除
- 不可回退的结构变更（删字段、改类型）

## 5. 检查清单

**发布前**
- [ ] 本次改动在 dev 跑过，集成测试通过
- [ ] 新增正式表已加入白名单
- [ ] 字段变更 SQL 已准备，并在 dev 执行过
- [ ] 配置项变化已同步到 prd 的 `config/app.env`

**发布后**
- [ ] 健康检查通过
- [ ] 关键页面、关键接口手动访问正常
- [ ] `bash opt/linux/sync_tables.sh` 显示两边一致
- [ ] 开发日志写了：发布内容、执行命令、手动 SQL、回滚方式

## 6. 回滚

- 代码：回到上一个发布的 commit 重新构建、重启。
- 表结构：新增表 / 字段一般不需要回滚；破坏性变更在发布前准备好反向 SQL。
- 发布前对 prd 做备份（`pg_dump`），备份位置写在开发环境说明里。

# doc/plan/

开发计划与技术方案。**实施前先写计划，确认后再动代码。**

命名：`YYMMDDHHmmV1_中文标题.md`，如 `2601151330V1_订单导出功能方案.md`。版本与状态规则见 [`doc/README.md`](../README.md)。

## 文件头

```markdown
# <标题>
日期：2601151330
状态：📝 设计中
确认：<谁、何时确认，如「负责人 2026-11-23 确认 §8 全部同意」>
```

## 必须有的部分

| 部分 | 回答 |
|---|---|
| 背景与目标 | 为什么做，做完解决什么问题 |
| **范围** | 做什么、**明确不做什么** |
| 设计 | 按需：数据库设计 / 接口设计 / 前端设计 / 核心逻辑 |
| 可行性核算 | 时间、成本、数据量算过账没有 |
| 里程碑 | **按可交付物切**，每个里程碑写验收方式 |
| 风险 | 哪里可能出错、出错怎么回退 |
| 待决项 | 需要负责人拍板的问题，拍板后写上结论和日期 |

小功能可以合并章节，但「范围」和「验收方式」不能省。

## 硬性约束

1. **"不做什么"要写**。范围边界比功能列表更能防止跑偏。
2. **要算账**。不能只写"很快""不贵"，写出估算和依据。
3. **里程碑按交付物切**。"用户能导出订单 Excel 了"是可验证的；"后端写完了"不是。
4. **数字可追溯**。阈值、容量、耗时要能指向来源：实测、文档，或明确标注"估计"。
5. **计划与实现冲突时，先改计划再改代码**，不在代码里偷偷偏离。
6. 涉及建表时先看 [`建表规范`](../doc/建表规范.md)，在计划里写出表名和字段。
